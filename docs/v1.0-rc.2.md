# v1.0.0-rc.2 — PDF rendering and navigation hotfix

Candidate **1.0.0 (11)**, application source `97438ec2f348f2c4d2c84541c4d665cc6298451e`. Test/CI targeting correction `b9758bdaba0d861ac0065944cf5c084954e75e23` leaves the production tree identical. Stable v1.0 remains undeclared. Library, source-file and anchor schemas are unchanged. Private books and derived private page images are not committed or uploaded.

## Root causes and correction

- PDFKit's Objective-C page loader bypassed Swift stored-property initializers in the observed runtime. Every AdaptivePDFPage had an empty render identifier, and uninitialized optional eligibility read as available. Adapted palettes reused one image across pages/documents and recolored ineligible pages. The page adapter is now stateless. An explicitly initialized document delegate owns locked eligibility results and a document namespace plus native CGPDFPage number. Preflight and draw share the same correct cache entry; complex/scan/dark pages preserve Original.
- In two-up modes currentDestination can describe the left page after a jump targets the right page. Incrementing the leading anchor by one repeatedly reopened the same spread. Relative controls now advance whole spreads using the visible focused page, honor a separate book-style cover and stop at bounds. Reader, Mini Reader and Split use the same calculation.
- PDFKit can retain an offscreen currentPage during manual/search scrolling. Such stale focus is discarded in favor of the visible-fragment anchor, so counters and commands follow the document. Geometric anchors still preserve the viewport; explicit page jumps retain their existing meaning.

The first final-source Foundation attempt passed 18 cases and skipped five, but failed to discover Mini Reader within five seconds in the window-close scenario. The captured video showed a blank desktop, the AX hierarchy marked the whole application disabled, and XCTest logged a commonInitWithApplicationSpecifier assertion. These observations do not establish an application root cause. [That failure is retained](../Research/v1.0-rc.2/foundation-first-attempt-summary.json); the unchanged-source retry reproduced the same discovery failure. The large-PDF scroll case passed in both attempts. Test-only correction b9758bd now captures the named Mini Reader item’s geometry once and clicks via the stable View menu-bar origin, avoiding MenuItem.click’s hover/re-resolution of SwiftUI’s shared menuAction: identifier. It additionally requires a running timer and the closed tools sheet. No lifecycle assertion was removed. The lifecycle case also runs in the fast release gate, while remaining in Foundation to retain ordered-suite coverage; this is one deliberate duplicate execution.

The original [rc.1 acceptance](v1.0.md) and measurements are historical and do not certify changed application source. The prior regression gap was checking navigation/text metadata or the standalone renderer without asserting distinct images drawn by PDFKit-created subclasses. New tests cover this boundary directly.

The exact macOS 15.0 runtime, fresh system VoiceOver/Reduce Motion/Transparency review, downloaded/quarantined Gatekeeper installation and actual old-binary replacement on a clean Mac remain open stable-release gates. Real-model evaluation remains owner-deferred. No model is enabled, no protection is bypassed and no source document is rewritten.
