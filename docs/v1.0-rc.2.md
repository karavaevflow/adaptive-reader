# v1.0.0-rc.2 - PDF rendering and spread navigation hotfix

Candidate version **1.0.0 (11)**. This fixes two user-visible defects in rc.1; stable v1.0 remains undeclared. Existing library/source/anchor schemas are unchanged. The user's PDF and library are not test fixtures and are not committed or uploaded.

## Root causes and correction

- Native PDFKit page loading bypassed the Swift stored-property initializers of AdaptivePDFPage in the observed runtime. Every page had an empty render identifier, and uninitialized optional eligibility read as available. Selected palettes reused one image across different pages/documents and incorrectly recolored ineligible pages. AdaptivePDFPage is now stateless; the explicitly initialized document delegate owns locked eligibility results and a document namespace plus native CGPDFPage number. Preflight and draw share the same correct cache entry. Complex/scan/dark pages preserve Original.
- In two-up modes PDFKit's currentDestination can describe the left page even after navigation targets the right page. Controls incremented that leading anchor by one, repeatedly reopening the same spread. Relative PDF navigation now uses PDFKit's focused page, advances to the next/previous spread, honors a separate book-style cover and stops at bounds. This also handles tall continuous viewports where the saved leading fragment belongs to the preceding page. A focused page outside the viewport is stale after manual/search scrolling and is discarded in favor of the geometric anchor (covered by a separate large-document regression). The counter reflects the visible focused page; geometric anchors still preserve the viewport. Main Reader, Mini Reader and the secondary pane use the same engine calculation; explicit page jumps and saved visible-fragment anchors retain their existing meaning.
